# 오늘의 필름 백엔드 — 구조 설명서

이 문서는 `backend/` 폴더의 모든 파일이 무엇이고, 서로 어떻게 맞물려 돌아가는지 설명한다.

---

## 1. 큰 그림: 백엔드가 하는 일

백엔드는 Flutter 앱과 AI(Gemini) 사이의 중간 관리자다. 앱은 백엔드하고만 대화하고, AI 호출·데이터 저장은 전부 백엔드가 대신 처리한다.

```
Flutter 앱  ──HTTP 요청──▶  백엔드(FastAPI)  ──▶  DB (기록 저장)
                                │
                                └──▶  Gemini API (질문/필름 생성)
```

이렇게 중간에 백엔드를 두는 이유는 두 가지다. 첫째, Gemini API 키를 앱에 넣으면 누구나 추출해서 내 비용으로 AI를 쓸 수 있다(키는 서버에만 존재해야 한다). 둘째, "질문 다시 받기 3회 제한" 같은 규칙은 서버에서 강제해야 우회가 불가능하다.

## 2. 폴더 구조와 역할

```
backend/
├── requirements.txt      # 이 프로젝트가 쓰는 파이썬 라이브러리 목록
├── .env.example          # 환경변수 견본 (.env로 복사해서 사용)
├── README.md             # 실행 방법, API 목록
│
└── app/                  # 실제 코드 전부
    ├── main.py           # 🚪 입구
    ├── config.py         # ⚙️ 설정
    ├── database.py       # 🔌 DB 연결
    ├── models.py         # 🗄️ DB 테이블 정의
    ├── schemas.py        # 📋 요청/응답 형식 정의
    ├── security.py       # 🔐 비밀번호/토큰
    ├── deps.py           # 🎫 로그인 확인
    ├── routers/          # 📮 API 창구들
    ├── services/         # 🧠 비즈니스 로직
    └── ai/               # 🤖 AI 연동
```

폴더 세 개의 역할 분담이 핵심이다:

- **routers/** — 창구. 앱의 요청을 받아 검사하고, 실제 일은 services에 넘긴다. 은행 창구 직원처럼 "신분증 확인 → 담당 부서 연결"만 한다.
- **services/** — 실무자. "질문을 만들려면 사진을 리사이즈하고, 이전 답변을 모으고, AI를 호출하고, 결과를 저장한다" 같은 실제 업무 순서를 안다.
- **ai/** — AI 전담 통역사. services가 "질문 하나 만들어줘"라고 하면 Gemini가 알아듣는 형식으로 번역해서 호출한다. **Gemini를 Claude로 바꿔도 이 폴더만 수정하면 되는 구조.**

## 3. 파일별 설명

### 루트 파일

| 파일 | 역할 |
|---|---|
| `requirements.txt` | `pip install -r requirements.txt` 로 설치할 라이브러리 목록 |
| `.env.example` | 설정값 견본. `.env`로 복사한 뒤 Gemini API 키 등을 채운다. `.env`는 비밀값이라 git에 올리면 안 됨 |
| `README.md` | 실행 방법, API 전체 목록, 운영 배포 전 할 일 |

### app/ — 코어 파일

| 파일 | 역할 | 언제 수정하나 |
|---|---|---|
| `main.py` | 서버의 입구. 앱을 생성하고 모든 창구(라우터)를 등록한다. `uvicorn app.main:app` 이 이 파일을 실행하는 것 | 새 라우터를 추가할 때 |
| `config.py` | `.env`의 값을 읽어 코드 전체에 제공. 질문 개수(3개), 업로드 용량(40MB), AI 모델명 등 모든 정책 수치가 여기 있다 | 정책 수치를 바꿀 때 |
| `database.py` | DB 연결 관리. 개발은 SQLite 파일, 운영은 PostgreSQL로 `.env`만 바꾸면 전환 | 거의 수정할 일 없음 |
| `models.py` | DB 테이블 설계도. "기록은 user_id, 날짜, 제목…을 가진다"는 정의. 서버 시작 시 이 정의대로 테이블이 자동 생성됨 | 저장할 데이터 항목이 늘 때 |
| `schemas.py` | API 통신 규격서. "회원가입 요청에는 email, password, nickname이 와야 한다"는 정의. 형식이 틀리면 FastAPI가 자동으로 거부 | API 입출력 형식이 바뀔 때 |
| `security.py` | 비밀번호 암호화(bcrypt) + 로그인 토큰(JWT) 발급/검증 | 거의 수정할 일 없음 |
| `deps.py` | "이 요청, 로그인한 사용자 맞아?"를 확인하는 공용 검문소. 모든 API가 이걸 통과해야 함 | 거의 수정할 일 없음 |

### app/routers/ — API 창구

| 파일 | 담당 API | 하는 일 |
|---|---|---|
| `auth.py` | `/auth/*` | 회원가입, 로그인, 내 정보, 계정 삭제 |
| `photos.py` | `/photos/*` | 사진 업로드 (1~5장, 40MB 제한, 형식 검사) |
| `records.py` | `/records/*` | **핵심 창구.** 기록 생성 → AI 질문 → 답변 저장 → 필름 생성 → 조회/수정/삭제 |
| `archive.py` | `/archive/*` | 월간 캘린더, 키워드 검색, '과거의 오늘' |
| `moments.py` | `/moments/*` | 낮에 남기는 순간 메모 (밤 회고 때 AI 참고자료가 됨) |
| `voice.py` | `/voice/*` | 음성 파일 → 텍스트 변환(STT) |
| `reports.py` | `/reports/*` | 월간/연간 회고 리포트 |

### app/services/ — 실무 로직

| 파일 | 하는 일 |
|---|---|
| `reflection.py` | **가장 중요한 파일.** 회고 전체를 지휘한다: 몇 번째 질문인지 판단 → 사진/순간메모/날씨를 참고자료로 준비 → AI 호출 → 필름 저장 → 과거 기록 연결까지 |
| `embeddings.py` | 기록을 숫자 벡터(임베딩)로 바꿔 저장하고, "의미가 비슷한 과거 기록"을 찾는다. "취업 걱정"과 "첫 출근"을 연결하는 게 이 파일 |
| `reports.py` | 한 달/일 년치 기록을 모아 AI 리포트 생성. 비용 때문에 한 번 만든 리포트는 DB에 저장해두고 재사용 |
| `weather.py` | 위치 좌표 → 날씨 조회 (Open-Meteo 무료 API). 실패해도 회고를 막지 않음 |
| `images.py` | AI에 보내기 전 사진을 1024px로 압축. 원본을 그대로 보내면 AI 비용이 몇 배로 뜀 |

### app/ai/ — AI 연동 (교체 가능한 구조)

| 파일 | 하는 일 |
|---|---|
| `base.py` | "AI라면 이 6가지를 할 수 있어야 한다"는 계약서(인터페이스): 질문 생성, 필름 생성, 연결 문장, 임베딩, 음성 전사, 리포트 |
| `gemini.py` | 그 계약서를 Gemini로 이행하는 구현체. **현재 사용 중** |
| `mock.py` | 가짜 AI. API 키 없이도 서버가 돌아가게 해줌 (개발/테스트용) |
| `factory.py` | `.env`의 `AI_PROVIDER` 값을 보고 gemini/mock 중 선택. Claude 추가 시 여기 분기 하나 추가 |
| `prompts.py` | **AI에게 주는 지시문 전부.** "감정을 단정하지 마라, 오글거리지 않게 써라" 같은 PRD 원칙이 코드로 담긴 곳. 문체 튜닝은 이 파일만 수정 |

## 4. 실제 동작: 회고 한 번의 여정

사용자가 밤에 회고를 하면 내부에서 이런 일이 벌어진다.

**① 사진 업로드** — 앱이 사진 2장을 `POST /photos/upload`로 전송 → `photos.py`가 형식·용량 검사 후 디스크 저장, DB에 메타데이터 기록.

**② 기록 생성** — `POST /records` → `records.py`가 "오늘 이미 필름 있나?" 확인(하루 1개 원칙) → 위치가 있으면 `weather.py`가 날씨 조회 → DB에 기록 생성.

**③ 첫 질문** — `POST /records/{id}/questions` → `reflection.py`가 지휘 시작: 대표 사진을 `images.py`로 1024px 압축 + 오늘의 순간 메모/장소/날씨를 참고자료로 묶음 → `factory.py`가 고른 AI에게 전달 → `gemini.py`가 `prompts.py`의 지시문("감정을 단정하지 마라...")과 함께 Gemini 호출 → *"이 사진을 오늘의 대표 장면으로 고른 이유가 있을까요?"* 반환, DB 저장.

**④ 답변** — `POST /records/{id}/answers` → 답변 저장. 질문③↔답변④를 3회 반복. 2·3번째 질문은 이전 답변을 읽고 이어서 만든다 (사진은 다시 안 보냄 — 비용 절약).

**⑤ 필름 생성** — `POST /records/{id}/film` → `reflection.py`가 답변 전체를 AI에 넘겨 제목·엔딩 내레이션·대표 문장·키워드 생성 → `embeddings.py`가 이 기록을 벡터로 저장 → 과거 기록 중 의미가 비슷한 것 탐색(없으면 키워드 겹침으로 재시도) → 찾으면 AI가 연결 문장 생성: *"몇 달 전 취업 걱정이 오늘은 새로운 시작으로 이어졌네요."*

**⑥ 아카이브** — 이후 앱은 `GET /archive/calendar`로 캘린더를, 기록이 3개 이상 쌓이면 `GET /reports/monthly`로 월간 리포트를 받아볼 수 있다.

## 5. DB 테이블 요약

| 테이블 | 저장하는 것 |
|---|---|
| `users` | 사용자 계정 (비밀번호는 암호화 저장) |
| `daily_film_records` | 하루 기록의 본체. 제목/내레이션/대표문장 + 위치/날씨. **(user_id, date) 조합 중복 불가 = 하루 1필름** |
| `photos` | 사진 파일 경로 + 대표 사진 여부 |
| `ai_questions` / `user_answers` | 질문과 답변 (건너뛴 것도 기록) |
| `memory_keywords` | 필름 키워드 (검색·연결용) |
| `memory_links` | "이 기록 ↔ 저 과거 기록" 연결 + 연결 문장 |
| `moments` | 낮에 남긴 순간 메모 |
| `record_embeddings` | 기록의 의미 벡터 (기억 연결용) |
| `reports` | 생성된 월간/연간 리포트 캐시 |

## 6. 자주 할 수정, 어디를 고치면 되나

| 하고 싶은 것 | 수정할 곳 |
|---|---|
| AI 말투/질문 스타일 바꾸기 | `ai/prompts.py` |
| Gemini 모델 버전 변경 | `.env` 의 `GEMINI_*_MODEL` |
| Claude로 교체 | `ai/gemini.py` 복사해 구현 → `ai/factory.py` 등록 → `.env` 변경 |
| 질문 개수, 업로드 용량 등 정책 | `.env` (코드 수정 불필요) |
| 새 API 추가 | `routers/`에 파일 추가 → `main.py`에 등록 |
| 저장 항목 추가 | `models.py` + `schemas.py` (개발 중엔 `todaysfilm.db` 삭제 후 재시작) |
